How I developed this

A test that would take 15 seconds

git switch -c ufo

My first updateUfo() called millis() itself. It worked in the game, but when I came to write testUfoArrivesOnTime(), I couldn't: the tests run once, as the page loads, when millis() is close to 0. The only way to see a UFO arrive would be to wait at least 15 seconds.

So I made the time a parameter, updateUfo(now). The game passes in millis(); the tests pass in whatever time they need. The retrospective in PLAN.md lists this as one of the lessons of the whole project.

The UFO that came straight back

In my first version, the code for a UFO leaving the screen set ufo to null and scheduled the next one. The code for shooting it only set ufo to null. So after I shot a UFO, nextUfoTime was still the time the old one had been due, which was already in the past, and a new UFO appeared on the very next frame.

I shot a UFO, and another was already flying in from the edge, worth different points. I added a check to testShootingTheUfo() that shooting the UFO schedules the next one, watched it fail, and then put both lines into removeUfo(), called from both places. Now the two can't get out of step.

The bug hunt plants a different bug in the same spot: removeUfo() forgets to schedule the next UFO. Because both places use it, that one mistake shows up both ways.

Making it testable without waiting

Even with tests, I wanted to see each case in the real game without waiting up to 25 seconds each time. The console let me summon a UFO whenever I liked:

nextUfoTime = millis()

Version 1.0

With the UFO merged, every feature in the plan was done. Before tagging a release, I:

  • updated the Progress section of PLAN.md for stages 12 to 15;
  • wrote a Retrospective: what went well, what I'd do differently, and ideas for version 2;
  • wrote CHANGELOG.md, one entry per version, using the stage tags to find each version's commits.

Then I tagged the release with an annotated tag, which stores a message, the date and who made it, unlike the plain tags from stages 8 and 11.

Manual checks

  • A UFO appears 15 to 25 seconds after the game starts (watch the overlay's countdown).
  • It comes from the left sometimes and the right sometimes, and crosses the whole screen.
  • Shooting it scores 50, 100, 150 or 300, and plays the explosion.
  • After it leaves or is shot, the next one is 15 to 25 seconds away.
  • A new game has no UFO on screen.
  • The console shows only PASS lines.

The commits, and the release

git commit -am "Fix: schedule the next UFO after shooting one"

git switch main
git merge ufo
git branch -d ufo
git commit -am "Plan: progress and retrospective; add changelog"
git tag -a v1.0 -m "Version 1.0: every feature in the plan"
