Programming concepts

Time, not frames: millis()

Until now, everything has been counted in frames: move 2 pixels per frame, a small chance of firing each frame. But "every 15 to 25 seconds" is about time. A game doesn't always run at exactly 60 frames a second, so counting frames would make the wait longer on a slow computer.

p5's millis() gives the number of milliseconds (thousandths of a second) since the sketch started. 15 seconds is 15000 milliseconds.

Scheduling: "when is the next one due?"

To make something happen later, store when it should happen, then keep checking whether that time has come:

nextUfoTime = now + random(UFO_MIN_WAIT, UFO_MAX_WAIT);   // decide when

if (now >= nextUfoTime) {                                // check, every frame
    ufo = spawnUfo();
}

random(15000, 25000) gives any number from 15000 up to (but not including) 25000, so each wait is different. The check uses >=, not ===: millis() jumps by about 16 each frame, so it would almost never be exactly equal to nextUfoTime.

Passing the time in

updateUfo() needs to know the time. It could call millis() itself, but then a test would have to really wait 15 seconds to see a UFO arrive. Instead, the time is a parameter:

updateUfo(millis());   // the game: the real time
updateUfo(5000);       // a test: "pretend it's 5 seconds in"

The function can't tell the difference. The tests can now jump to any moment instantly: just before the UFO is due, just after, or ten seconds later. It's the same idea as stage 12's speed parameter, and stage 2's move(direction): a function that's given what it needs is easy to test.

null again: "no UFO"

Most of the time there isn't a UFO. As with the single bullet in stage 3, ufo is null when there's nothing there, and the code checks ufo === null or ufo !== null before using it.

Picking from a list: random(array)

Given an array, p5's random() returns one item from it, chosen at random:

random([50, 100, 150, 300])   // 50, 100, 150 or 300

One function, used in two places

A UFO goes away in two ways: it flies off the screen, or it's shot. Either way, two things must happen: ufo becomes null, and the next UFO is scheduled. Writing those two lines in both places would let them get out of step: fix one, forget the other. So they're in one function, removeUfo(), and both places call it.

Finishing a project

The last feature isn't the last job. This stage also:

  • adds a Retrospective to PLAN.md: what went well, what to do differently, and ideas for a version 2;
  • writes a changelog: every version, in words a player understands (commit messages are written for developers);
  • tags the release in Git as v1.0, so it can always be found again.
