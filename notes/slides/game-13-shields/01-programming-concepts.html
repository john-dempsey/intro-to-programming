Programming concepts

One function, any kind of target

Since stage 7, handleCollisions() has checked bullets against aliens. Shields need the same check, twice: player bullets against blocks, and alien bullets against blocks. That's three almost identical nested loops.

Look at what the check actually uses from an alien: only getBounds(). It never looks at the alien's colour or points. So if a shield block also has a getBounds() method, returning the same kind of object, the same loop works for blocks:

collideBulletsWith(bullets, aliens);          // player bullets against aliens
collideBulletsWith(bullets, shieldBlocks);    // player bullets against shields
collideBulletsWith(alienBullets, shieldBlocks);  // alien bullets against shields

JavaScript doesn't check what kind of object is in the list. When the loop calls targetList[targetIndex].getBounds(), all that matters is that the object has a method with that name. Stage 15 will use the same function for the UFO.

Return what happened; let the caller decide what it means

The old function returned points. But a shield block isn't worth any points, so a general function can't add them up. Instead, collideBulletsWith() returns an array of the targets that were hit, and the code that called it decides what to do with them. For aliens, that means adding up their points. For shield blocks, it means nothing: the blocks are already removed, and the return value is ignored.

Refactoring, with the tests as a safety net

Refactoring means changing how code is written without changing what it does. handleCollisions() still exists, with the same name, the same parameters and the same result. Inside, it's now two lines built from smaller functions. The tests written for it in stages 7 and 9 didn't change at all, and they all still pass. That's how you know the refactor didn't break anything.

Refactor first, check the tests pass, commit, and only then add the new feature. If something breaks, you'll know whether it was the refactor or the feature.

Spacing things evenly

To spread 4 shields across a 640-pixel canvas with equal gaps, divide the width into 5 equal parts (one more than the number of shields) and put a shield at each dividing line:

let centreX = width * (shield + 1) / (shieldCount + 1);
shieldcentreX
0640 × 1 / 5 = 128
1640 × 2 / 5 = 256
2640 × 3 / 5 = 384
3640 × 4 / 5 = 512

This works for any number of shields: change SHIELD_COUNT and they spread out evenly on their own.

One array for every block

The four shields could have been four arrays. But nothing in the game ever needs to know which shield a block belongs to: a bullet either hits a block or it doesn't. So all the blocks go in one array, shieldBlocks, and the game handles them with one loop. Store data in the shape the code needs, not the shape it looks like on screen.
