Programming concepts

Automatic tests

So far, you've checked sketches by running them and looking. That works, but you have to remember to look at everything, every time. An automatic test is code that checks other code: it runs a piece of the program and compares what happened with what should have happened.

This stage's tests use one small function, check():

function check(description, actual, expected) {
    if (actual === expected) {
        console.log("PASS: " + description);
    } else {
        console.error("FAIL: " + description + " (expected " + expected + ", got " + actual + ")");
    }
}
  • description says what's being checked, in plain words.
  • actual is the value the code really produced.
  • expected is the value it should have produced.

console.error() works like console.log(), but the message appears in red, so failures stand out.

Professional developers use testing frameworks (such as Jest or Mocha) that do the same job with more features. The idea is exactly the same: actual versus expected.

A test must be able to fail

A test that always passes, whatever the code does, is useless. When you write a new check, make it fail once on purpose (change the expected value) to prove it's really checking something.

Catching errors: try / catch

try {
    testShipConstructor();
    testShipStartPosition();
} catch (error) {
    console.error("A test crashed: " + error.message);
}

Normally, if a line of code causes an error (calling a method that doesn't exist, for example), the program stops. try runs a block of code; if anything inside it causes an error, the program jumps to the catch block instead of stopping. error.message describes what went wrong. Here it means a broken test is reported, but the game still runs.

Two script files

index.html now loads two files:

<script src="sketch.js"></script>
<script src="tests.js"></script>

Both files share the same global variables and functions, so setup() in sketch.js can call runTests() from tests.js. That works because p5 waits until every file has loaded before it calls setup(). Keeping the tests in their own file keeps sketch.js about the game.

The debugger

Every modern browser has a debugger in its developer tools (F12). It lets you:

  • set a breakpoint on a line, so the program pauses when it gets there;
  • look at the value of every variable at that moment (the Scope panel);
  • step over one line at a time (F10), watching values change;
  • resume (F8) to carry on until the next breakpoint.

It answers the question "what is the program actually doing?" without adding console.log() lines everywhere. In a p5 sketch, remember that draw() runs about 60 times a second, so a breakpoint inside it pauses straight away, every frame.
